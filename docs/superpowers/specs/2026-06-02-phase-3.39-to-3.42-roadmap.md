# Phase 3.39 – 3.42 — Red-team phishing feature roadmap

Four sequential feature phases that build on the Phase 3.32 – 3.38 infrastructure (dim mode, audit log, recipient PII encryption) to give TAPhish operators concrete red-team capability that the upstream SniperPhish never shipped.

Order is by ROI per engagement hour. Each phase ships as its own PR + deploy.

---

## Phase 3.39 — Pretext + landing-page template library

**The gap.** Operators today start every engagement from a blank `MailTemplate` and an empty `SiteCloner` URL. The most-used scenarios (M365 login, IT password reset, vendor invoice, CEO ask) are re-built from scratch every time.

**The change.** A curated, in-app library:

- 12 starter pretext templates organized by category: **Authentication** (M365, GSuite, Okta, generic SAML), **Finance** (invoice, payroll error, expense report), **HR** (benefits enrolment, policy attestation), **IT** (password reset, MFA enrolment, security alert), **Shipping** (FedEx, UPS, DHL).
- Each entry: subject line, HTML body with `{{merge_field}}` placeholders, recommended landing-page slug, suggested category tag.
- One-click "Use this template" copies to the operator's `tb_core_mailcamp_template_list` so they can customize without touching the seed.
- New page `spear/PretextLibrary.php` — gallery layout under `body.dim-panel`.
- New dispatcher actions on `userlist_campaignlist_mailtemplate_manager.php`: `list_pretexts`, `clone_pretext_to_my_templates`.

**Storage.** New table `tb_core_pretext_library(id, kind ENUM('email'), category, name, subject, body, tags, created_at)`. Seeded idempotently at session-manager boot the same way `taphish_ensure_mail_presets` works.

**No new dependencies.** Plain PHP + the existing Summernote editor for the preview.

## Phase 3.40 — Anti-scanner detection on tracker + landing pages

**The gap.** M365 SafeLinks, Proofpoint URL Defense, Mimecast, and Cisco Umbrella fire a GET against every link in every email seconds after delivery. Each hit currently counts as a "click" in the dashboard and pollutes the engagement data. Worse: a scanner that fetches a credential-capture page may flag the URL as malicious before the real recipient ever opens the email.

**The change.** Inline filter on the public tracker + landing endpoints (`track.php`, `qt.php`, `mod.php`, cloned-site router):

- Pure helper `spear/manager/scanner_detect.php` → `taphish_classify_visitor(string $ua, string $ip, int $secondsSinceSent): array` returning `['kind' => 'real'|'scanner'|'suspect', 'reason' => '...']`.
- Detection signals: known scanner UA substrings (`SafeLinks`, `Proofpoint`, `Mimecast`, `urldefense`, `barracuda`, `office365`, `microsoft office`, `outlook`, `bingbot`, `Trustwave`), datacenter ASNs surfaced via reverse-DNS PTR (`compute-1.amazonaws.com`, `azurewebsites.net`, `googleusercontent.com`), abnormally fast hits (< 5 s after the campaign's send timestamp), missing or malformed `Referer`.
- Default action: log the hit under a separate severity, return a 200 with a benign `<h1>Loading…</h1>` body so the scanner sees "clean", and **do not** mark the recipient as engaged.
- New audit kind: `SCAN` (severity `warn`). Updates `log_classifier.php` accordingly.

**Tests.** Pure classifier in `tests/ScannerDetectTest.php` with fixtures covering each detection signal + a "real recipient" baseline.

## Phase 3.41 — Homoglyph domain generator + DMARC analyzer

**The gap.** Two pre-engagement steps every operator does manually today:

1. Generate visually-similar attacker domains (`tаrget.com` with cyrillic `а`, `target.co`, `target-corp.com`, etc.).
2. Inspect the target's SPF / DKIM / DMARC posture to decide whether direct spoofing or look-alike is the move.

**The change.** Two pure helpers + a new page `spear/SenderToolkit.php`:

- `spear/manager/homoglyph.php` → `taphish_homoglyph_candidates(string $domain): array` returning a ranked list of look-alikes plus a "confusability score" per candidate. Sources: cyrillic/greek look-alike map, common-typo map (qwerty-neighbours), TLD swap (`.com → .co/.io/.net/.org/.com.co`), word-boundary insertion (`target → target-corp`, `target-llc`).
- `spear/manager/dmarc_lookup.php` → `taphish_lookup_email_posture(string $domain): array` using `dns_get_record()` for the SPF (`TXT v=spf1`), DKIM (`TXT _domainkey.*`), and DMARC (`TXT _dmarc.*`) records, plus a recommendation string ("DMARC p=reject — direct sender spoofing infeasible, prefer a look-alike domain").

**Both are pure.** Homoglyph helper covered by unit tests; DMARC lookup is integration (real DNS) so the unit suite mocks `dns_get_record`.

## Phase 3.42 — Credential + 2FA capture + operator alerting

**The gap.** The current webform submit endpoint captures fields the cloned site asks for, but offers no first-class 2FA handling and no real-time notification. Operators discover engagement results by refreshing the dashboard.

**The change.**

- Schema: add `code_2fa VARCHAR(16) NULL` to `tb_data_webform_submit` (idempotent migration in session_manager boot).
- Template helper: when an operator clones a site with a 2FA step, the cloned form includes an optional 2FA input bound to the same submit endpoint.
- Webhook dispatch: on first capture per `(campaign_id, recipient)`, POST a JSON payload to a configurable Slack / Teams / Discord webhook URL stored in `tb_core_settings`. Generic JSON shape: `{campaign, recipient_name, recipient_email, captured_at, summary}`. Webhook URL is at-rest encrypted via the existing `secret_at_rest_seal()` pattern.
- PDF report stub: a `download_engagement_report` action on `web_mail_campaign_manager.php` that builds a simple PDF (TCPDF, already in `spear/libs`) with: campaign name, send timestamp, recipient roster summary (counts only, no PII), click + capture timeline, and the operator's notes.

**Tests.** Webhook payload builder + recipient-de-dup tracker as pure helpers in `tests/CaptureAlertingTest.php`. PDF generator is integration.
