# Phase 3.48b — Per-engagement PII isolation (RBAC requirement #4)

> Design spec. Closes the deferred follow-up from Phase 3.48: recipient/user-group
> reads are currently operator-coarse (any operator sees every recipient list).
> This scopes them to the engagements an operator belongs to.

**Goal:** an operator can see and act on a recipient user-group only if it belongs
to an engagement they are a member of. Super-admin sees all (consistent with the
rest of RBAC). The at-rest PII encryption (`user_data`, Phase 3.38) is unchanged —
this is purely about **row visibility**, not the cipher.

**Tech:** PHP 8.1+ (mysqli), existing AES-256-GCM envelope, PHPUnit 10.5. Mirrors
the Phase 3.45b campaign-FK migration + the Phase 3.48 authz patterns.

---

## Why this is needed

`tb_core_mailcamp_user_group` holds recipient PII (`user_data`, encrypted) but has
no engagement/owner column, and every read runs with no `WHERE` filter:

- `get_user_group_list`, `pullMailCampaignFieldData` (the campaign-builder dropdown),
  and the paginated table read all return **all** groups to **all** operators.
- A campaign references its user-group only as JSON inside `campaign_data` (no FK),
  so a group's engagement can't be reliably derived at query time.

Phase 3.48 enforced engagement scoping for actions that *carry* an `engagement_id`,
but user-group actions don't — so they were left operator-coarse and documented as
deferred. This phase closes that gap.

---

## Resolved decisions

1. **Legacy rows (engagement_id NULL):** one-time backfill from campaign references;
   anything not unambiguously derivable stays NULL and **remains visible to all
   operators** (no lockout on deploy). Tightening NULL handling is a later, separate
   call. — *Safest rollout.*
2. **Sharing model:** one user-group belongs to exactly **one** engagement. Reuse
   across engagements is not offered for new groups; legacy rows are untouched.
3. **Standalone creation** (the `MailUserGroup` "Create New → User Group" page, which
   has no engagement context): a **required engagement selector** is added so every
   new group is stamped.

---

## Architecture

### Schema migration (idempotent, boot-time)

`taphish_user_group_ensure_engagement_column(\mysqli $conn): void` — mirrors
`taphish_engagement_ensure_campaign_fk_column`. Wired into the `session_manager.php`
boot sequence alongside the other ensure-migrations.

```sql
ALTER TABLE tb_core_mailcamp_user_group
  ADD COLUMN engagement_id INT UNSIGNED NULL DEFAULT NULL;
CREATE INDEX idx_user_group_engagement ON tb_core_mailcamp_user_group(engagement_id);
```

Both guarded by INFORMATION_SCHEMA existence checks so re-runs are no-ops.

### One-time backfill

Runs **only inside the "column was just added" branch** of the migration (single
pass; never re-scans on subsequent boots). For each NULL group:

- Collect the `engagement_id`s of every campaign in `tb_core_mailcamp_list` whose
  `campaign_data` JSON references that group id.
- If they resolve to exactly **one** non-null engagement → stamp the group with it.
- Zero references, or references spanning multiple engagements (ambiguous) → leave NULL.

The decision logic is a **pure reducer** so it's unit-tested without a DB:

```php
// returns int engagement_id to stamp, or null to leave unscoped
function taphish_user_group_backfill_engagement(array $campaignRefs): ?int
// $campaignRefs = [['engagement_id' => int|null], ...] for campaigns referencing the group
```

### Visibility helpers (`authz.php`)

```php
// engagement ids the user is a member of (from tb_core_engagement_member)
function taphish_user_engagement_ids(\mysqli $conn, string $username): array;

// pure decision: may this role/membership see a group with this engagement_id?
//   super-admin → true; engagement_id === null → true (legacy/all-operators);
//   engagement_id ∈ memberIds → true; else false.
function taphish_user_group_visible(?int $groupEngagementId, string $role, array $memberIds): bool;

// dispatcher guard for single-row user-group ops: resolves the group's
// engagement_id, applies taphish_user_group_visible; deny → 403 +
// {result:'forbidden'} + audit log + exit (same shape as taphish_require_authorize_or_die).
function taphish_user_group_guard_or_die(\mysqli $conn, string $group_id): void;
```

### Data flow

**List reads** (`get_user_group_list`, `pullMailCampaignFieldData`, paginated table):
- super-admin → existing query, unfiltered.
- operator → append `WHERE engagement_id IS NULL OR engagement_id IN (<member ids>)`
  (parameterised; empty member set still shows NULL groups).

**Single-row ops** (`getUserGroupFromGroupId`, `download_user`, `save_user_group`
rename path, `delete_user_group_from_group_id`, `make_copy_user_group`): call
`taphish_user_group_guard_or_die($conn, $group_id)` before touching the row.

**Stamping at creation:**
- `uploadUserCVS` persists the `engagement_id` it already receives (when > 0).
- `save_user_group` (new group) accepts `engagement_id`; the `MailUserGroup` page
  gains a required engagement `<select>`.
- `make_copy_user_group` inherits the source group's `engagement_id`.
- On any stamp, validate the operator is a member of that engagement
  (`taphish_engagement_role` non-null, or super-admin) → else forbidden. Prevents
  stashing PII into an engagement the operator can't see.

**Cron is untouched:** `mail_campaign_cron.php` reads groups as the system (no
session). Scoping lives only in the operator dispatcher handlers, so scheduled sends
never get blocked. (Explicit non-change, called out so no one "helpfully" adds it.)

### Policy

Tiers stay operator+ (`get_user_group_*`, `save_user_group`, etc. unchanged). The new
enforcement is **row-level inside the handlers** via the helpers above — user-group
actions don't carry an `engagement_id` in the request, so resolving the group's
engagement in-handler is cleaner than re-routing through the dispatcher guard.

### UI

- `MailUserGroup.php`: required engagement selector on create (lists the operator's
  engagements; super-admin sees all). Show the owning engagement on the list/header.
- The campaign-builder user-group dropdown now only offers accessible groups
  (handled by the scoped `pullMailCampaignFieldData`).

## Error handling

- Denied single-row access → `{result:'forbidden'}` + HTTP 403 + `logIt('Forbidden
  user-group <id> attempted by <user>')` (classifies AUTH/warn via the existing
  Phase 3.35 classifier). No soft empty 200.
- Stamping to a non-member engagement → `{result:'failed', error:'…'}` (or forbidden),
  no row written.
- Missing/invalid engagement on standalone create → validation error, no insert.

## Testing

- **Pure:** `taphish_user_group_visible` truth table (super-admin / NULL / member /
  non-member / empty member set); `taphish_user_group_backfill_engagement` (zero refs
  → null, single engagement → that id, multi-engagement → null, NULL engagement refs
  ignored).
- **Structural:** migration helper defined + idempotent (existence-checked).
- DB-backed handlers (list scoping, guard) follow the codebase norm of not being
  unit-tested without a DB; verified via the running app where practical.

## Migration safety

- Column is nullable + indexed; legacy NULL = visible to all → **no operator lockout**
  on deploy.
- Backfill only fills unambiguous cases; never overwrites a non-null value.
- Rollback: dropping the column is safe once the code that reads it is also rolled
  back (standard additive-migration pattern, same as 3.45b).

## Non-goals

| Out of scope | Why |
|---|---|
| Re-encrypting existing PII rows | That's the separate roadmap item "3.49 PII re-encrypt sweep". |
| Locking NULL groups down to super-admin | Deliberately deferred (decision #1) to avoid disruption; revisit later. |
| Many-to-many group↔engagement sharing | Decision #2 — one group, one engagement. |
| Scoping templates / senders / trackers by engagement | This phase is recipient PII only. |
| Per-engagement row-level audit-log visibility | Already deferred to a future phase in the 3.48 plan. |
