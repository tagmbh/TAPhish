# Phase 3.49 — Recipient PII re-encrypt sweep

**Status:** design approved (decisions delegated to implementer; "it just must work when done")
**Date:** 2026-06-04
**Depends on:** Phase 3.38 (at-rest envelope), Phase 3.48b (`engagement_id` on the table)

## Problem

Recipient PII lives in `tb_core_mailcamp_user_group.user_data` (a JSON array of
`{uid, fname, lname, email, notes}` recipients). Phase 3.38 seals it at rest with
AES-256-GCM (`enc1:<base64(IV+tag+ciphertext)>`), but the seal is **lazy**: a row is
only encrypted the next time it is written. Two gaps follow:

1. **Pre-3.38 rows** imported before encryption shipped sit in plaintext until edited.
2. **Key-unavailable writes** silently store plaintext — `recipient_data_seal()`
   returns the input unchanged (and logs a warning) when `secret_at_rest_get_key()`
   is `null`. Any row written during a window where `spear/config/secret.key` was
   missing/unreadable is plaintext on disk.

The lazy "next-write-encrypts" pattern never closes these gaps on its own.

## Goal

A re-runnable maintenance command that **forces the at-rest invariant**: every
`user_data` row is either empty or `enc1:`-sealed when it finishes. Idempotent —
already-sealed rows are skipped, so it is safe to run repeatedly.

## Scope (locked)

- **What:** seal lingering *plaintext* `user_data` rows with the **current** key.
  No key rotation, no second key. (Rotation is explicitly out of scope.)
- **Coverage:** `tb_core_mailcamp_user_group.user_data` **only**. SMTP/IMAP
  passwords, the webhook URL, and BeEF creds are out of scope for this phase.
- **Trigger:** **CLI only** — `spear/manager/cli/reencrypt_recipient_pii.php`,
  run over SSH like `grant_super_admin.php`. No web action, no boot-time auto-run.

## Non-goals (YAGNI)

- Key rotation / multi-key handling.
- Web/UI trigger or dispatcher action (the core logic is structured so one could be
  added later with no change to the helper).
- Sweeping any column other than `user_data`.
- Decrypting and re-displaying PII — the command never emits recipient contents.

## Architecture

Three files. No existing read/write path changes — the sweep is additive and offline.

| File | Role | Tested |
|---|---|---|
| `spear/manager/recipient_reencrypt.php` | **Pure logic.** Per-row planner, run-orchestrator, summary formatter. No mysqli, no argv, no I/O — all DB/crypto access is injected. | Unit, offline |
| `spear/manager/cli/reencrypt_recipient_pii.php` | **Thin driver.** CLI guard, bootstrap, key gate, row stream, apply UPDATEs, print report, audit line. | Lint only (repo convention: CLI bootstrap scripts are not unit-tested) |
| `tests/RecipientReencryptTest.php` | Unit tests with a fixed 32-byte test key + injected seams. | — |

`recipient_reencrypt.php` must be registered in `tests/Support/helpers_shim.php` so
the suite loads it (the suite has no DB; it relies on the shim).

### Boundaries

- The **planner** knows nothing about mysqli or argv. Given one stored string plus
  crypto closures, it returns a decision. That is the entire interface.
- The **orchestrator** knows nothing about crypto internals or the console. Given an
  iterable of rows, an "apply update" closure, the crypto closures, and a dry-run
  flag, it loops, calls the planner, applies updates (unless dry-run), and returns a
  summary struct. Pure given its injected seams — so the loop logic (tally, dry-run,
  verify-before-write) is unit-tested with fakes, no DB.
- The **driver** wires the real `recipient_data_seal` / `recipient_data_unseal` /
  `secret_at_rest_is_encrypted` and a mysqli row generator + prepared-UPDATE closure
  into the orchestrator, then renders the summary.

This mirrors `recipient_import.php` (pure) ↔ its dispatcher caller, and
`grant_super_admin.php` (CLI bootstrap template).

## Component contracts

### Per-row planner

```php
/**
 * Classify one stored user_data value and produce the action to take.
 *
 * @param string|null $stored   raw column value
 * @param callable $sealFn      fn(string $plaintextJson): string   (real: recipient_data_seal)
 * @param callable $unsealFn    fn(?string): ?string                (real: recipient_data_unseal)
 * @param callable $isEncFn     fn(?string): bool                   (real: secret_at_rest_is_encrypted)
 * @return array{action:string, reason:string, sealed:?string, suspect:bool}
 *   action ∈ {'skip-empty','skip-sealed','seal','error'}
 *   sealed  is the value to write back, set only when action === 'seal'
 *   suspect is informational only — true when a sealed value did not look like a
 *           recipient array (does not change the action; the value is still sealed)
 */
function taphish_reencrypt_plan_user_data($stored, callable $sealFn, callable $unsealFn, callable $isEncFn): array
```

Decision table:

| Input | action | write? |
|---|---|---|
| `null` or `''` | `skip-empty` | no |
| starts with `enc1:` (`isEncFn` true) | `skip-sealed` | no |
| any other non-empty plaintext, seals + round-trips cleanly | `seal` | yes (`sealed` set) |
| plaintext, but seal result is not `enc1:`-prefixed, or unseal ≠ original | `error` | no (reported) |

**Design note — seal everything, don't gate on JSON shape.** The goal is *no plaintext
PII at rest*. The round-trip check guarantees byte-exact preservation, so a value that
does not `json_decode` to a recipient array is still sealed (it is plaintext that
shouldn't be on disk either) — it is merely flagged `suspect: true` for the report.
Leaving it plaintext "because it looked malformed" would defeat the phase. A JSON
recipient array starts with `[`, never `enc1:`, so there is no false-positive against
the sealed check.

**Seal-then-verify-then-write** (the `seal` path):
1. `$sealed = $sealFn($stored)`.
2. If `!$isEncFn($sealed)` → `error` (seal silently passed through — e.g. key vanished
   mid-run; never write back unsealed plaintext).
3. If `$unsealFn($sealed) !== $stored` → `error` (round-trip mismatch; never risk PII loss).
4. Otherwise `seal` with `sealed = $sealed`; set `suspect = !is_array(json_decode($stored, true))`.

### Run orchestrator

```php
/**
 * @param iterable $rows  each: array{user_group_id:string|int, user_data:?string}
 * @param callable $applyUpdate  fn(string|int $id, string $sealed): bool   (no-op semantics under dry-run: not called)
 * @param array $crypto  ['seal'=>callable,'unseal'=>callable,'isEnc'=>callable]
 * @param bool $dryRun
 * @return array{scanned:int, skipped_empty:int, skipped_sealed:int, sealed:int,
 *               suspect:int, errors:int, write_failures:int,
 *               suspect_ids:array, error_ids:array, sealed_ids:array}
 */
function taphish_reencrypt_run(iterable $rows, callable $applyUpdate, array $crypto, bool $dryRun): array
```

- For each row: call the planner; increment the matching counter.
- On `seal` and **not** dry-run: call `$applyUpdate($id, $sealed)`; if it returns
  false, increment `write_failures` (and record the id) — the row stays plaintext,
  surfaced for re-run.
- On `seal` and dry-run: count it under `sealed` but do not call `$applyUpdate`.
- When a `seal` row is `suspect`, also bump `suspect` and record the id (informational;
  the row is still sealed/written).
- Collect ids for `suspect`, `error`, and `sealed` (capped list for readable output;
  full counts always accurate).

### Summary formatter

```php
function taphish_reencrypt_format_summary(array $counts, bool $dryRun): string
```

Renders a human-readable block, e.g.:

```
Recipient PII re-encrypt sweep
  scanned:         42
  already sealed:  38 (skipped)
  empty:            1 (skipped)
  sealed:           3
  suspect:          1 (sealed, but not a recipient array — group_id 17)
  errors:           0
  write failures:   0
[DRY RUN — no rows written]
```

## CLI driver

`spear/manager/cli/reencrypt_recipient_pii.php`, following `grant_super_admin.php`:

1. **CLI-only guard:** `php_sapi_name() !== 'cli'` → 403 + die.
2. **Argv:** `--dry-run` (report only, write nothing) and `--verbose` (list affected
   ids). Anything else → usage to STDERR, exit 2.
3. **Bootstrap:** `require_once .../config/db.php` (gives `$conn`); abort (exit 1) if
   `$conn` is not a mysqli. `require_once .../manager/secret_at_rest.php` and
   `.../manager/recipient_reencrypt.php`.
4. **Key gate (hard):** call `secret_at_rest_get_key()`. If `null` → print a clear
   error ("at-rest key unavailable at spear/config/secret.key — refusing to run so we
   never store plaintext") and **exit 1**. Without this, a keyless run would "succeed"
   while sealing nothing, because `recipient_data_seal()` passes plaintext through.
5. **Row stream:** `SELECT user_group_id, user_data FROM tb_core_mailcamp_user_group`,
   yielded one row at a time (generator) — never loads all PII into memory at once.
6. **Apply closure:** a reused prepared statement
   `UPDATE tb_core_mailcamp_user_group SET user_data=? WHERE user_group_id=?`,
   returning success boolean. (`engagement_id` is untouched.)
7. **Run + report:** call `taphish_reencrypt_run(...)`, then print
   `taphish_reencrypt_format_summary(...)`.
8. **Audit line:** `logIt("recipient PII re-encrypt sweep: sealed N of M rows" .
   ($dry ? " (dry-run)" : "") . "; malformed=X errors=Y", 'system')` attributed to a
   CLI actor (no web session). Records who/when/how-many for the operator's trail.
9. **Exit codes:** `0` success (including nothing-to-seal); `1` key-unavailable / DB /
   connection error; `2` bad usage. Non-zero if any row ended in `error` or
   `write_failures` (so a wrapping cron/script can detect an incomplete sweep).

### Safety properties

- **Never writes plaintext back.** The only `UPDATE` carries a value that passed
  `isEnc` and round-trip checks.
- **Idempotent.** Re-running after a clean pass scans, finds everything `skip-sealed`,
  writes nothing, exits 0.
- **Crash-safe.** Per-row autocommit UPDATEs; a mid-run crash leaves already-sealed
  rows sealed and the rest plaintext — a re-run finishes the job.
- **Memory-safe.** Streaming generator, one row at a time.
- **No PII in output or logs.** Reports counts and `user_group_id`s only — never
  names, emails, or recipient JSON.

## Error handling

| Condition | Behavior |
|---|---|
| At-rest key missing/unreadable | Abort before touching any row; exit 1. |
| Row value already `enc1:` | Skip (idempotent). |
| Row value empty/null | Skip. |
| Plaintext not a recipient array | Seal anyway (round-trip verified); flag `suspect` in report. |
| Seal returns non-`enc1:` (key vanished mid-run) | `error`; report id; do not write. |
| Seal/unseal round-trip mismatch | `error`; report id; do not write. |
| `UPDATE` fails | `write_failures`; report id; row stays plaintext for re-run. |
| DB connection absent | Abort; exit 1. |

## Testing (`tests/RecipientReencryptTest.php`, offline, fixed key)

Planner:
- null / `''` → `skip-empty`.
- `enc1:...` → `skip-sealed`.
- valid recipient-array plaintext (`[{"uid":"...","email":"..."}]`) → `seal`,
  `sealed` starts `enc1:`, unseals back to the original, `suspect` false.
- non-array plaintext (`"not json"`, `"123"`) → `seal` with `suspect` true (still
  sealed + round-trips).
- injected `sealFn` that returns input unchanged (simulated keyless) → `error`.
- injected `sealFn` whose `unsealFn` round-trips wrong → `error`.

Orchestrator:
- mixed batch (sealed + empty + plaintext + suspect) → exact counts; `applyUpdate`
  called only for `seal` rows with the sealed value; `suspect` tallied separately.
- dry-run: `applyUpdate` never called; `sealed` count still reflects would-seal rows.
- `applyUpdate` returns false → counted under `write_failures`, not `sealed`.

Formatter:
- counts struct → expected lines present; dry-run banner appears only under dry-run.

Use real `secret_at_rest_encrypt/decrypt` with a fixed `str_repeat("\x42",32)` key
(as `SecretAtRestTest` does) to wire realistic seal/unseal closures; use trivial
fakes for the failure-injection cases.
