# Phase 3.55 — Look-alike domain deployment + DNS helper

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Once an operator owns a look-alike domain (e.g. `texti1color.ch`, the `l→1` look-alike of `textilcolor.ch`), give them a one-screen flow to (a) publish a cloned/library landing page onto that domain or a subdomain of it, and (b) get the exact DNS records to paste at their registrar so the page resolves + mail authenticates. Two hosting modes: **operator-hosted** (their own webspace on the look-alike domain) or **TAPhish-hosted** (served under `ptbe.autodiscover.li` with a vanity path).

**Architecture:** A new "Deploy landing page" surface that ties together three things TAPhish already has — the landing library (Phase 3.46) / site cloner, the DKIM generator (Phase 3.45c), and the SPF/DMARC analyzer (Phase 3.41). It produces (1) a deployable site bundle, (2) a copy-paste DNS record set (A/AAAA or CNAME + SPF + DKIM + DMARC), and (3) a host target. No registrar API integration in v1 — the operator pastes records manually (their registrar varies; Hostpoint, Cloudflare, etc.).

**Tech Stack:** PHP 8.1+ (mysqli), existing landing_library + dkim_helper + dmarc_lookup + domain_check, PHPUnit.

## Worked example (used throughout)

- **Target:** `textilcolor.ch`
- **Look-alike (owned):** `texti1color.ch`
- **Goal:** publish an M365-style capture page at `https://login.texti1color.ch/` (subdomain) or `https://ptbe.autodiscover.li/p/texti1color-login/` (TAPhish-hosted), with DNS that makes the page resolve and mail from `@texti1color.ch` pass SPF/DKIM/DMARC.

## Threat model + non-goals

This feature operationalizes a look-alike domain. It's appropriate ONLY for authorized engagements where the operator already controls the domain. Constraints:

**Hard requirements.**
1. The look-alike domain must be operator-supplied + confirmed owned. The UI states "only deploy to domains you are authorized to use for this engagement." We do not register domains.
2. TAPhish-hosted mode serves the page under a per-engagement vanity path on the existing host — it never auto-provisions DNS for someone else's domain.
3. DKIM private keys are shown once (Phase 3.45c pattern) and never persisted server-side in plaintext.
4. Generated DNS records are advisory text — TAPhish never writes to a registrar.
5. Every deploy emits an audit-log entry (engagement id + domain + mode).

**Non-goals (YAGNI).**

| Out of scope | Why |
|---|---|
| Registrar API integration (auto-create DNS) | Registrars vary; manual paste is universal + auditable. Future per-registrar adapters. |
| TLS cert issuance for the look-alike domain | Operator-hosted mode is their webspace's job; TAPhish-hosted uses the existing wildcard/host cert. |
| Auto-registering the look-alike | We validate (Phase 3.54) but never buy. |
| Mail-sending from the look-alike | Separate sender config; this phase only emits the DNS so it *could* authenticate. |

## Two hosting modes

### Mode A — TAPhish-hosted (fastest)
Serve the landing page under the existing host at a vanity path:
`https://ptbe.autodiscover.li/p/<slug>/`. The operator points the look-alike at it with a single CNAME (or just uses the ptbe URL in the lure). DNS the operator pastes:
- Optional: `login.texti1color.ch. CNAME ptbe.autodiscover.li.` (so the lure shows their look-alike while content is TAPhish-hosted — note TLS will warn unless the operator also fronts it; document this tradeoff).
- For mail auth from `@texti1color.ch`: SPF + DKIM + DMARC records (below).

### Mode B — operator-hosted (cleanest lure)
Operator downloads the site bundle (zip of the cloned/library page with `{{POST_URL}}` pre-substituted to point back at `https://ptbe.autodiscover.li/track.php`) and uploads it to their own webspace on `texti1color.ch`. DNS the operator pastes:
- `texti1color.ch. A <their-webspace-ip>` (or the subdomain).
- SPF + DKIM + DMARC for mail auth.

Both modes produce the same DNS-record helper output; only the web-hosting target differs.

## The DNS-record builder (the core)

`lookalike_build_dns_records($domain, $opts)` returns an ordered list of records, each `{type, host, value, note}`:

```
For texti1color.ch, mode=hosted, selector=s1, cname_target=ptbe.autodiscover.li:

  [
    {type:'CNAME', host:'login.texti1color.ch.', value:'ptbe.autodiscover.li.',
     note:'Points the look-alike subdomain at the TAPhish-hosted page (TLS caveat).'},
    {type:'TXT',   host:'texti1color.ch.',
     value:'v=spf1 include:<your-sender> -all',
     note:'SPF — authorizes your sending host. Replace <your-sender>.'},
    {type:'TXT',   host:'s1._domainkey.texti1color.ch.',
     value:'v=DKIM1; k=rsa; p=<public-key>',
     note:'DKIM — from the key pair generated below.'},
    {type:'TXT',   host:'_dmarc.texti1color.ch.',
     value:'v=DMARC1; p=none; rua=mailto:<you>',
     note:'DMARC — p=none while warming; tighten to quarantine/reject later.'},
  ]
```

All pure string construction — no DNS writes, no network. Reuses `dkim_helper` for the DKIM record and `domain_check_local_idna` so an IDN look-alike (umlaut) gets punycode `host` values.

Tasks 1–2 build + test this; it's the highest-value, lowest-risk piece.

## Open questions (with recommendations)
1. **TLS for the look-alike in TAPhish-hosted mode.** A CNAME to ptbe means the browser sees a cert for ptbe, not the look-alike → warning. Recommendation: document the tradeoff; default the lure to the raw `ptbe.autodiscover.li/p/<slug>/` URL (valid cert) and treat the look-alike CNAME as an advanced option. A proper fix (per-domain cert via ACME) is a future phase.
2. **Bundle vs live-pull for operator-hosted.** Recommendation: zip bundle download (works on any webspace) for v1; an SFTP push adapter is a future add.
3. **Where the look-alike domain is stored.** Recommendation: on the engagement (new nullable `lookalike_domain` column) so the deploy page can prefill it and the DNS helper is one click from EngagementView.

## Out-of-band notes
This phase deliberately stops at "emit the DNS records + host the page." It does NOT touch the registrar or send mail — those stay manual/separate so the operator keeps an auditable boundary between "TAPhish generated advice" and "operator acted on it." If you later want registrar automation, that's a per-registrar adapter phase with its own credentials-at-rest story.
