# Phase 3.48 — Multi-operator + RBAC

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Introduce role tiers (super-admin / operator / read-only) and engagement-scoped permissions so multiple operators can run concurrent engagements without seeing each other's recipient data, while keeping the single-admin install path working unchanged.

**Architecture:** Additive role column on `tb_main`; one nullable `engagement_id` membership column or a new join table for per-engagement scoping; a central `taphish_authorize($conn, $action, $context)` guard that every dispatcher path calls; per-operator API tokens stored encrypted-at-rest via the existing Phase 3.38 envelope. NO change to the existing `admin` account — it auto-promotes to super-admin on first migration.

**Tech Stack:** PHP 8.1+ (mysqli), existing AES-256-GCM envelope, PHPUnit 10.5.

---

## Threat model + non-goals

This is the most operationally invasive change since 3.38 (PII encryption). Auth is on the request path for every operator action; getting it wrong locks out the admin or — worse — silently grants access that shouldn't exist. The whole plan is structured to make THAT specific failure mode visible and recoverable.

**Hard requirements (do not violate).**

1. **The existing `admin` account MUST stay working.** Idempotent migration; super-admin role assigned on first boot if the row exists.
2. **Default-deny on unknown actions.** The central guard returns false for any (role, action) pair not in the policy table. New dispatcher actions are unreachable until policy explicitly admits them.
3. **No silent degradation.** If a user lacks permission, the dispatcher returns `{result: 'forbidden', error: '…'}` with a 403 — never a soft 200 with empty data. Easier to spot during audits.
4. **PII isolation is engagement-scoped.** Operator A querying recipients for an engagement they don't belong to gets the forbidden response, NOT empty results. The visibility boundary is engagement membership, not a filter.
5. **Audit-log every forbidden response.** Phase 3.35 logger emits `AUTH/warn: forbidden <action> by <user>` so an operator probing the edges leaves a trail.
6. **Migration is reversible.** The `role` column has a safe default ('operator' for existing rows except `admin`); rolling back to a build without RBAC keeps everyone logged in.
7. **API tokens go through the same guard.** Per-operator API tokens (long-lived, bearer) authenticate as the operator and then pass through `taphish_authorize` — they don't get a separate trust path.

**Non-goals (explicit YAGNI list).**

| Out of scope | Why |
|---|---|
| Federation / SAML / OIDC login | Out of scope — local accounts only for v1. Future phase. |
| Resource quotas per operator | Not what RBAC is for. |
| UI for invitation flows / password reset emails | Super-admin creates accounts; password reset stays the existing self-service path. |
| Soft-delete / suspended accounts | A row in `tb_main` with `role='disabled'` covers it; no separate workflow. |
| Audit-log row-level visibility (operators can't see each other's events) | Phase 3.51 audit log scoping; deferred to a follow-up. |

## Schema changes

### `tb_main` — add `role`

```sql
ALTER TABLE tb_main
  ADD COLUMN role VARCHAR(32) NOT NULL DEFAULT 'operator';
-- One-shot during migration: promote the bootstrap admin.
UPDATE tb_main SET role = 'super-admin' WHERE username = 'admin';
```

Allowed values: `super-admin`, `operator`, `read-only`, `disabled`.

### `tb_core_engagement_member` — new join table

```sql
CREATE TABLE tb_core_engagement_member (
  engagement_id INT      NOT NULL,
  user_id       INT      NOT NULL,
  role          VARCHAR(32) NOT NULL DEFAULT 'operator',
  created_at    BIGINT   NOT NULL,
  PRIMARY KEY (engagement_id, user_id),
  KEY (user_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

`role` is engagement-scoped — e.g., a super-admin can still be a `read-only` member on a specific engagement to keep their actions to view-only on that one.

### `tb_main_api_token` — new

```sql
CREATE TABLE tb_main_api_token (
  id              INT AUTO_INCREMENT PRIMARY KEY,
  user_id         INT NOT NULL,
  token_hash      VARCHAR(255) NOT NULL,
  label           VARCHAR(128) NOT NULL,
  last_used_at    BIGINT NULL,
  created_at      BIGINT NOT NULL,
  revoked_at      BIGINT NULL,
  KEY (user_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

Token is bcrypt-hashed (same `verify_user_password` path as session passwords). The plaintext is shown ONCE at creation and never again — exactly the GitHub PAT pattern.

All three migrations are idempotent + run via `session_manager.php` boot path (same Phase 3.45a/3.45b/3.52 pattern).

## Central authorization guard

`spear/manager/authz.php` (NEW):

```php
function taphish_authorize(\mysqli $conn, string $action, array $context = []): bool;
function taphish_user_role(\mysqli $conn, string $username): string;
function taphish_engagement_role(\mysqli $conn, int $engagement_id, string $username): ?string;
function taphish_require_authorize_or_die(\mysqli $conn, string $action, array $context = []): void;
```

**Policy table** (pure data, lives at the top of the file):

```php
const TAPHISH_POLICY = [
    // action  =>  required role tiers (any-of); 'engagement_member' means
    //             the user must be a member of $context['engagement_id'].
    'view_home'               => ['*'],
    'view_audit_log'          => ['super-admin'],
    'export_audit_log'        => ['super-admin'],
    'list_engagements'        => ['*'],
    'save_engagement'         => ['super-admin', 'operator'],
    'view_engagement'         => ['engagement_member'],
    'export_engagement_pdf'   => ['engagement_member'],
    'transition_engagement_status' => ['super-admin', 'engagement_owner'],
    'save_campaign'           => ['engagement_member'],
    'send_campaign'           => ['engagement_member'],
    'view_recipients'         => ['engagement_member'],
    'upload_recipients'       => ['engagement_member'],
    'beef_settings_*'         => ['super-admin'],
    'beef_list_hooks'         => ['*'],
    'library_clone_to_my_sites' => ['operator', 'super-admin'],
    'site_clone'              => ['operator', 'super-admin'],
    'manage_users'            => ['super-admin'],
    'manage_api_tokens'       => ['super-admin'],
    // ...one entry per dispatcher action.
];
```

Wildcard `*` = any authenticated user (including read-only). `engagement_member` = the user appears in `tb_core_engagement_member` for `$context['engagement_id']`. `engagement_owner` = same plus role='owner' on that membership.

**Default-deny** if an action isn't in the policy table.

## Migration safety net

Two mechanisms make this rollback-safe:

1. **Column default + admin auto-promote.** Schema rollback to a pre-3.48 build leaves everyone logged in because the missing column just becomes `''` and no code reads it.
2. **Recovery escape hatch.** Add `spear/manager/cli/grant_super_admin.php` — a CLI-only script (gated on `php_sapi_name() === 'cli'`) that promotes a username to super-admin even if RBAC locks the operator out of the UI. Documented in PROGRESS.md.

## Open questions intentionally left in the plan

1. **Engagement membership semantics for super-admin.** Recommendation: super-admin implicitly satisfies `engagement_member` checks. Trade-off: less granular but matches operator mental model.
2. **Read-only role scope.** Recommendation: read-only across the whole platform (no engagement-level granularity). Operators who need granular read access get added as `read-only` members of a specific engagement instead.
3. **API token expiry.** Recommendation: no automatic expiry for v1 — operators revoke manually. Add expiry in a future phase if operator feedback warrants it.
4. **Forbidden response vs. 404.** Recommendation: explicit 403 + `{result: 'forbidden'}`. Information leak ("does this engagement exist?") is acceptable in operator context vs. opaque 404s that make debugging painful.
